## 背景与问题

用户在 P0001 最小闭环达成当天重新定位：项目就叫 **Reader**，定位是 **Agent 原生文档阅读、搜索和提取工具**。原定位「PDF 文档文本搜索与提取工具」只描述了格式与动作，没有说清服务对象与设计导向：工具首先是给 Agent（AI 智能体）管线调用的，人是第二受众。定位变了，输出形态与演进优先级跟着变。

## 目标与非目标

- 目标：
  - 全仓定位文档对齐新口径（AGENTS 定位节、README、R001、ROADMAP、CHANGELOG）。
  - 「Agent 原生」落成可执行的设计约束，不是口号（见方案节）。
  - R001 按命名规范随定位改名，全仓引用与索引同步。
- 非目标：
  - 不改代码与 CLI 形态（reader/rr 双 bin、search/extract 语义不变）。
  - 不新增格式支持（PDF 仍是首个且当前唯一格式；docx/html/md 等按需另立项）。
  - 不上 JSON 输出（列为阶段 3 首要候选，立项再做）。

## 方案

新定位三段式：

1. **本质**：Reader 是 Agent 原生文档阅读、搜索和提取工具：为 Agent 管线设计的 CLI，从本地文档读文本层：按页读、按词/正则搜、按页取。
2. **Agent 原生的设计约束**（落到行为，验收可查）：
   - 输出稳定可解析：行式标记输出（`页:行号:文本`、`== page N ==`），退出码 grep 语义（0/1/2），不输出装饰性内容到 stdout。
   - 单调用完成一件事，无交互、无守护进程、无环境副作用；错误走 stderr。
   - 机器可读优先于人类美观：后续输出形态演进（JSON 等）以此为序。
3. **边界**：服务对象先 Agent 后人；不做 GUI/TUI 交互式阅读器；文档首版只读 PDF；保持纯 Rust 单二进制。
4. **命名**：显示名 Reader；仓库 `reader_rs` 沿用；CLI `reader`（缩写 `rr`）不变。
