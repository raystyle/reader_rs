## 背景与问题

安全牛扫描 PDF 81 页全 needs_ocr 触发 S006，研究实证纯 Rust 管线（hayro 渲染加 pure-onnx-ocr 跑 PP-OCRv5 mobile）可行。用户指示接续开发，把 `--ocr` 兜底落进产品。

## 目标与非目标

- 目标：
  - extract 与 search 对 PDF 单文件的 needs_ocr 页加 `--ocr` 兜底：hayro 渲染页为位图，tract 推理出行级文本回填 lines；`needs_ocr` 标记保留（OCR 文本仍属不可靠）。
  - 模型三件（det 加 rec 加 dict 共约 20.5MB）首用从 ModelScope RapidAI/RapidOCR 下载进平台缓存目录，SHA-256 钉死校验；`--offline` 禁下载；`READER_OCR_CACHE_DIR` 环境变量覆盖缓存目录。
  - 默认行为零变化（无 `--ocr` 时 stdout 逐字节不变；stderr 提示语改为指引入 `--ocr`）。
- 非目标：
  - 不做 OCR 质量调优（server 模型、PP-OCRv6 对比留 S006 待办 2）；不做平台原生 API 路线。
  - 不做批量目录加 OCR 组合（目录加 `--ocr` 报错退出 2）；模型不 include_bytes 内嵌。
  - 不发版本（封版另立项）。

## 方案

新模块 `src\ocr.rs`：`ensure_models`（缓存命中校验加下载加进程内 strip）加 `ocr_pages`（hayro 渲染加引擎推理）；`pdf.rs` 对 needs_ocr 页回填；`document.rs` 出 `OcrOpts`；`lib.rs` 两子命令加 `--ocr` / `--offline`。

模型件双套哈希钉死：

| 件 | 原件 SHA-256（ModelScope 官方） | stripped 件 SHA-256（本进程输出） |
| --- | --- | --- |
| det | `4d97c44a20d30a81aad087d6a396b08f786c4635742afc391f6621f5c6ae78ae` | `a4a307dbf6d7a18f3b021abdfecea6bf8a0b4124e707380b6f2918425fa5a30c` |
| rec | `5825fc7ebf84ae7a412be049820b4d86d77620f204a041697b0494669b1742c5` | `0b5e82dc8cb0e28e66c541848f4392d5da73e5b0d0afb0b559dce872ee656f3c` |
| dict | `d1979e9f794c464c0d2e0b70a7fe14dd978e9dc644c0e71f14158cdf8342af1b` | 同左（不 strip） |

stripped 哈希钉的是本进程 prost strip 的确定性输出，与 S006 PoC 的 Python onnx 序列化字节不同（功能等价，真样本 OCR 输出一致）；这是落地期实测后的裁决修正。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| 进程内 prost strip（选定） | 零新增重型依赖（prost 加 tract-onnx 本就随引擎进树）；下载源保持官方原件 |
| 分发预 strip 模型 | 需自托管模型仓，引入分发面维护成本 |
| 模型 include_bytes 内嵌 | 二进制 7.3MB 涨到约 28MB（S006 关键结论 5），弃 |
| 引擎进 static 复用 | OcrEngine 非 Send/Sync（M011），且构建仅约 29ms，每次现建即可 |

## 实施步骤

1. 立项登记三原语；ModelScope API 核对三件 URL 与哈希。
2. vendor pure-onnx-ocr 进 `vendor\`（max_width 2560 修复随带），Cargo.toml patch 加依赖（hayro、ureq、sha2、prost、tract-onnx、image）。
3. `src\ocr.rs` 与 `--ocr` 接线；`tests\cli.rs` 负例与环境门控冒烟。
4. 真样本回归（安全牛 PDF 两页加首用下载全流程）；门禁全绿。
5. 文案收口（introspect 双文本、SKILL 再生成、AGENTS、INDEX、CHANGELOG、diary、mistakes 沉淀）。

## 风险与回滚

- 风险：二进制体积 7.3MB 涨到 32.9MB（hayro 加 tract 加 image）。缓解：接受（S006 已认账量级）；将来可按 cargo feature 拆分，回滚 `git revert`。
- 风险：mobile 模型系统性掉字，OCR 文本误导调用方。缓解：`needs_ocr` 标记保留加 stderr 明示掉字；SKILL 写明限制。
- 风险：ModelScope 源件变动。缓解：SHA-256 钉死，变了即报错不静默跑错模型。

## 实施过程与经验

- 实际怎么做：按计划走完。真样本回归两页出正文（掉字符合 S006 预期）；首用下载全流程（下载加源件校验加 strip 加 stripped 校验加缓存加推理）实测打通；search `--ocr` 命中扫描页正文。
- 与计划偏差一：stripped 件哈希计划钉 PoC 的 Python strip 输出，实测 prost 编码字节不同，改钉本进程输出（见方案节裁决修正）。
- 与计划偏差二：vendored 引擎库代码 `println!` 打日志污染 stdout（PoC 未暴露，落地回归才见），vendor 补丁转 `eprintln!`（M010）。
- 沉淀的经验：ureq 默认响应体上限 10MB，rec 模型 16.6MB 直接撞限（M009）；OcrEngine 非 Send/Sync 不进 static，29ms 构建现建更省（M011）。
- 门禁联动：vendor 目录不进文档门禁（`.rumdl.toml` 与 `.tools` 双扫描器 SKIP_DIRS 加 `vendor`）。
