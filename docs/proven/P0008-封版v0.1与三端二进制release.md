# P0008-封版v0.1与三端二进制release

- 关联：TODO.md 当前目标 / P0004（CI 三系统矩阵，本方案复用其门禁面）

## 背景与问题

P0001–P0007 能力面已齐（search/extract、JSON 包膜、分页裁剪、agent 自省），CHANGELOG 的 Unreleased 攒了全部里程碑但代码尚未发布。用户点名封版 v0.1.0 并提供三端二进制 release 下载，让无 Rust 工具链的机器（含 mac/Linux 接管方）直接装。

## 目标与非目标

- 目标：
  - CHANGELOG 封版 `[0.1.0]`；git tag `v0.1.0`（与 Cargo.toml version 一致）。
  - `.github\workflows\release.yml`：tag `v*` 触发，四目标矩阵（windows x86_64、ubuntu x86_64、macos aarch64、macos x86_64）构建 release 二进制（`reader` 加 `rr`），打包上传 GitHub Release。
  - 流水线内置版本一致性闸（tag 与 Cargo.toml version 不一致即红）。
  - README 安装节补预编译二进制下载方式。
- 非目标：
  - 不做 linux-musl 静态链接、arm linux、包管理器分发（crates.io publish、brew、scoop 留候选）。
  - 不做签名与校验和之外的供应链加固（ checksums 文件随包出一份即可，见方案 3 条）。
  - 不改任何代码行为。

## 方案

1. tag 触发流水线：`on.push.tags: v*`；`permissions: contents: write`。
2. 矩阵四目标：`x86_64-pc-windows-msvc`（windows-latest）、`x86_64-unknown-linux-gnu`（ubuntu-latest）、`aarch64-apple-darwin`（macos-latest）、`x86_64-apple-darwin`（macos-13）；`cargo build --release --locked --target`。
3. 打包：暂存目录 `reader-<tag>-<target>/` 装 reader、rr、README、LICENSE、SKILL.md；Windows 出 zip（pwsh Compress-Archive），unix 出 tar.gz；每资产同出 `<资产名>.sha256` 校验文件（按目标命名，避免矩阵并发互相 clobber）。上传用 runner 自带 `gh` CLI（`GH_TOKEN`）：`gh release create ... || true` 幂等后按目标精确 glob `gh release upload --clobber`。
4. 版本闸：构建前 `grep -q "^version = \"${GITHUB_REF_NAME#v}\"$" Cargo.toml`。
5. README 安装节加「预编译二进制」小节（Releases 页链接加各资产命名规则）。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| gh CLI 上传（选定） | runner 自带、零新增第三方 action；create 加 `|| true` 天然幂等 |
| softprops/action-gh-release | 省事但引第三方 action；仓风格是最小外部动作面 |
| cargo-dist | 全功能发布编排（安装脚本、checksum、多包管理器），当前规模过度工程 |

## 实施步骤

1. 本方案立项，三原语登记。
2. release.yml 落地；CHANGELOG 封版；README 补下载节。
3. 门禁回归；INDEX/AGENTS/diary 登记。
4. 提交推送；打 tag v0.1.0 推 tag；盯 release run 三端资产齐出。
5. 验收：本机下载 windows 资产跑通 `reader --version` 与一次 search。

## 风险与回滚

- 风险：macos-13（intel）runner 退役（发布当日即发生，记 M004）。已落地：Intel 资产在 macos-latest 交叉编译，矩阵一行的事。
- 风险：矩阵并发抢建 release 竞态。缓解：`gh release create ... || true` 幂等；upload 用 `--clobber`。
- 回滚：删 tag 与 release（`gh release delete`）、revert workflow 提交。

## 实施过程与经验

- 实际怎么做：首发 run 33457730048 三 job 绿、Intel mac job 永久 queued——macos-13 runner 已被 GitHub 退役（症状是永久排队而非报错，记 M004 新分类 M104）。删半成品 release 与 tag，Intel 资产改 macos-latest 交叉编译（rust-toolchain `targets:` 加目标即够，同 SDK 双架构），重打 tag 重发（run 33461625241 四 job 全绿）。[实证: 2026-08-31 gh run view]
- 踩了什么坑 + 怎么解决：除 M004 外，首版打包草稿里四 job 同名 `sha256sums.txt` 并发上传会互相 clobber、上传 glob 会误匹配暂存目录——推送前自查改掉（按目标命名 `.sha256`、glob 精确到 `<tag>-<target>.*`）。合并 mac 侧验收登记时 GOAL/diary 冲突两处，手工并保留两侧记录。
- 沉淀的经验：
  - 退役 runner 的症状是 job 永久 queued 不是失败；矩阵选 runner 标签先查 GitHub 支持列表，异架构资产优先交叉编译而不是押注老 runner。
  - 矩阵并发上传 release 资产，校验文件必须按目标命名；上传 glob 要精确到扩展名，否则暂存目录也会匹配。
